## Objective

Define a comprehensive set of validation rules (minimum 5) that catch errors in haiku strings before execution. Establish an error taxonomy, specify validation pipeline order, and provide error recovery strategies. Each rule must include failing and passing test cases.

## Validation Rule Categories

```
┌─────────────────────────────────────────┐
│ Validation Pipeline (Sequential Order)  │
├─────────────────────────────────────────┤
│ 1. SYNTACTIC (BNF matching)             │
│    ├─ Operator keywords correct         │
│    ├─ Balanced parentheses/brackets     │
│    └─ Proper token sequence             │
│                                         │
│ 2. SEMANTIC (meaningful constructs)     │
│    ├─ IF requires THEN                  │
│    ├─ REQUIRES has states               │
│    └─ WARN has consequence              │
│                                         │
│ 3. REFERENTIAL (cross-references)       │
│    ├─ States referenced in REQUIRES     │
│      must be defined somewhere          │
│    ├─ REF: targets must exist           │
│    └─ Actions in THEN/ELSE valid        │
│                                         │
│ 4. COMPLETENESS (no missing info)       │
│    ├─ All REQUIRES states satisfiable   │
│    ├─ No circular dependencies          │
│    └─ All identifiers have definitions  │
│                                         │
│ 5. EXECUTION (pre-execution safety)     │
│    ├─ EXEC: commands syntactically OK   │
│    ├─ VERIFY: checks are automatable    │
│    └─ LOOP: iteration counts reasonable │
└─────────────────────────────────────────┘
```

## Validation Rules (5+ Required)

---

### **RULE-001: Syntactic Well-Formedness**

**ID:** VAL-001

**Name:** Syntactic Well-Formedness

**Severity:** Error (blocks execution)

**Description:**
The haiku string must match the BNF grammar from v0.0.2c. All operators must be correctly spelled, all brackets and parentheses must be balanced, and token sequence must follow grammar rules.

**Check Method:**
1. Tokenize input string
2. Parse against BNF productions
3. Report first syntax error with position

**Error Message:**
```
VAL-001 SYNTAX ERROR: {position}
  Expected: {expected_token}
  Found: {actual_token}
  Context: ...{before} ▶ {error} ◀ {after}...
```

**Example (Passing):**
```
Action:Deploy REQUIRES State:Online -> EXEC:deploy.sh
✓ PASS: All tokens valid, balanced, correct sequence
```

**Example (Failing):**
```
Action:Deploy REQUIRES State:Online -> EXEC:deploy.sh[
✗ FAIL: Unbalanced bracket at position 67
  Expected: statement or ']'
  Found: end-of-string
```

**Remediation:**
- Check operator spelling (case-sensitive)
- Balance all parentheses and brackets
- Ensure semicolons separate statements
- Use appropriate delimiters for commands (→ EXEC: or parentheses)

---

### **RULE-002: Operator Completeness**

**ID:** VAL-002

**Name:** Operator Completeness

**Severity:** Error

**Description:**
If an operator is present, its required clauses must also be present. For example, IF requires THEN; WARN requires a consequence identifier; LOOP requires count or WHILE clause.

**Check Method:**
1. Find all operator keywords in haiku
2. For each operator, check required complements
3. Report missing required complements

**Error Message:**
```
VAL-002 INCOMPLETE OPERATOR: {operator}
  Missing: {required_clause}
  Location: {position}
  Fix: Add '{required_clause}:' after '{operator}:'
```

**Example (Passing):**
```
IF:Condition THEN:Action:X ELSE:Action:Y
✓ PASS: IF has THEN, THEN has action
```

**Example (Failing):**
```
IF:Condition THEN
✗ FAIL: THEN clause has no statement
  Expected: action, condition, or reference after THEN:
```

**Another Failing Example:**
```
WARN:Skip_Backup
✗ FAIL: WARN missing consequence
  Expected: WARN:{id} -> {consequence}
```

**Remediation:**
- IF → must have THEN
- THEN → must have at least one statement
- WARN → must have `→ consequence`
- LOOP → must have count or WHILE clause
- REQUIRES → must have at least one state

### **RULE-003: Reference Definition**

**ID:** VAL-003

**Name:** Reference Definition (Semantic)

**Severity:** Error

**Description:**
All identifiers referenced in the haiku (States in REQUIRES, Actions in THEN/ELSE, conditions in IF, consequences in WARN) must be either defined in the haiku or documented in external references.

**Check Method:**
1. Extract all referenced identifiers (States, Actions, conditions)
2. Build definition table from haiku
3. For each reference, check if defined locally or externally resolvable
4. Report undefined references

**Error Message:**
```
VAL-003 UNDEFINED REFERENCE: {identifier}
  Category: {State|Action|Condition|Consequence}
  Used at: {position}
  Context: {statement_excerpt}
  Fix: Define '{identifier}' before use or document in REF:
```

**Example (Passing):**
```
Action:Backup REQUIRES State:DB_Online; Action:Deploy REQUIRES State:Backup_Complete
✓ PASS: State:DB_Online and State:Backup_Complete are defined/documented
```

**Example (Failing):**
```
IF:Deploy_Success THEN:Action:Verify
✗ FAIL: Deploy_Success not defined
  Expected: Definition as State:Deploy_Success or from prior action result
```

**Another Example (Failing):**
```
Action:Backup WARN:No_Backup -> Unknown_Consequence
✗ FAIL: Unknown_Consequence not defined
  Expected: Define what consequence occurs if backup is skipped
```

**Remediation:**
- Define states as `State:Identifier` in REQUIRES or postconditions
- Define actions before referencing in THEN/ELSE
- Document external identifiers in META: or REF:
- Use NOTE: to clarify ambiguous identifiers

### **RULE-004: Circular Dependency Detection**

**ID:** VAL-004

**Name:** Circular Dependency Detection

**Severity:** Error

**Description:**
A haiku must not contain circular dependencies where Action A requires State S1, which can only be achieved by Action B, which requires State S2, which can only be achieved by Action A. Such cycles are unsatisfiable.

**Check Method:**
1. Build dependency graph (State → Action → State edges)
2. Run depth-first search to detect cycles
3. If cycle found, report with path
4. Mark as unsatisfiable

**Error Message:**
```
VAL-004 CIRCULAR DEPENDENCY:
  Cycle: {State1} ← {Action1} → {State2} ← {Action2} → {State1}
  Location: {position}
  Impact: States cannot be satisfied; procedure is unsatisfiable
```

**Example (Passing):**
```
Action:Initialize REQUIRES State:Empty;
Action:Populate REQUIRES State:Initialized;
Action:Backup REQUIRES State:Populated
✓ PASS: Linear dependency chain (Empty → Initialized → Populated → Backed_Up)
```

**Example (Failing):**
```
Action:A REQUIRES State:X;
IF:X_Satisfied THEN:Action:B REQUIRES State:Y;
IF:Y_Satisfied THEN:Action:C REQUIRES State:X
✗ FAIL: Circular dependency detected (X → Y → X)
  Cycle path: X is required by A; X is set by C; C requires Y; Y is set by B; B requires X
  Fix: Break cycle by removing one dependency or making it optional
```

**Remediation:**
- Review REQUIRES clauses; identify which states are self-satisfied vs. action-provided
- Reorganize actions into topological order (DAG)
- Make optional dependencies into NOTE: instead of REQUIRES:
- Simplify procedures to avoid mutual dependencies

### **RULE-005: Verifiable Verification Checks**

**ID:** VAL-005

**Name:** Verifiable Verification Checks

**Severity:** Warning (execution may fail)

**Description:**
Each VERIFY: check must reference a testable condition. Vague or untestable verification names should be flagged. Examples of good verifications: `VERIFY:Service_Listening_On_Port_8080`, `VERIFY:Database_Responsive`. Bad examples: `VERIFY:Working`, `VERIFY:Good`.

**Check Method:**
1. Find all VERIFY: statements
2. Check if identifier is specific enough
3. Check against automated test catalog (if available)
4. Warn on non-automatable verifications

**Error Message:**
```
VAL-005 UNVERIFIABLE CHECK: {identifier}
  Category: {automatable|vague|external}
  Location: {position}
  Suggestion: {specific_identifier}
  Note: Verification '{identifier}' may require manual confirmation
```

**Example (Passing):**
```
Action:Start_Server -> EXEC:systemctl start postgresql;
VERIFY:PostgreSQL_Listening_On_5432
✓ PASS: Check is specific and automatable (netstat/ss)
```

**Another Passing Example:**
```
Action:Deploy -> EXEC:deploy.sh;
VERIFY:HTTP_200_Response_From_Health_Endpoint
✓ PASS: Check is testable (curl or HTTP client)
```

**Example (Failing):**
```
Action:Deploy -> EXEC:deploy.sh;
VERIFY:Deployment_OK
✗ WARNING: Verification check 'Deployment_OK' is vague
  Suggested: VERIFY:Service_Responding_To_Health_Check or VERIFY:Response_Code_200
  Note: Manual verification may be required
```

**Another Failing Example:**
```
Action:Upgrade -> EXEC:upgrade.sh;
VERIFY:Everything_Working
✗ WARNING: 'Everything_Working' is not automatable
  Suggested: VERIFY:Unit_Tests_Pass, VERIFY:Integration_Tests_Pass
  Note: Decoder cannot verify; requires human judgment
```

**Remediation:**
- Use specific, measurable criteria in VERIFY names
- Include what is being verified (service, port, response code)
- Reference external test suites if available
- Document how each VERIFY is checked in a mapping file
- For non-automatable checks, use NOTE: instead

---

### **RULE-006: REF Target Resolution** (Optional 6th Rule)

**ID:** VAL-006

**Name:** REF Target Resolution

**Severity:** Error

**Description:**
All REF: statements must point to valid, reachable documentation or procedures. Broken references should be reported with suggestions.

**Check Method:**
1. Find all REF: statements
2. Attempt to resolve target (file system, URL, documentation index)
3. Report broken or ambiguous references
4. Suggest correct targets

**Error Message:**
```
VAL-006 BROKEN REFERENCE: {target}
  Type: {file|url|section|procedure}
  Status: {not_found|ambiguous|unreachable}
  Location: {position}
  Suggestion: {suggestions}
```

**Example (Passing):**
```
IF:Deploy_Fail THEN:REF:Runbook-Deployment-v2.1:Error_Recovery
✓ PASS: Reference 'Runbook-Deployment-v2.1' exists; section 'Error_Recovery' found
```

**Example (Failing):**
```
IF:Deploy_Fail THEN:REF:Unknown_Runbook:Section
✗ FAIL: Reference target not found
  Available runbooks: Runbook-Deployment-v2.1, Runbook-Incident-Response
  Suggestion: Did you mean 'Runbook-Deployment-v2.1'?
```

**Remediation:**
- Check reference path exists in documentation repository
- Use exact names from reference catalog
- Create missing runbooks or sections before referencing
- Use version-specific references to avoid ambiguity

## Error Taxonomy

```
ERROR CATEGORIES AND CODES:

┌─ SYNTAX_ERROR (1xx)
│  ├─ VAL-101: Invalid operator keyword
│  ├─ VAL-102: Unbalanced bracket/parenthesis
│  ├─ VAL-103: Unexpected token sequence
│  └─ VAL-104: Invalid identifier format
│
├─ SEMANTIC_ERROR (2xx)
│  ├─ VAL-201: Incomplete operator (missing required clause)
│  ├─ VAL-202: Type mismatch (action vs. state)
│  ├─ VAL-203: Conflicting operators (e.g., THEN without IF)
│  └─ VAL-204: Invalid operator order
│
├─ REFERENTIAL_ERROR (3xx)
│  ├─ VAL-301: Undefined identifier
│  ├─ VAL-302: Undefined state
│  ├─ VAL-303: Undefined action
│  ├─ VAL-304: Circular dependency
│  └─ VAL-305: Broken reference (REF:)
│
├─ EXECUTION_ERROR (4xx)
│  ├─ VAL-401: Invalid command in EXEC:
│  ├─ VAL-402: Unverifiable check in VERIFY:
│  ├─ VAL-403: Invalid LOOP count
│  └─ VAL-404: Timeout or resource limit exceeded
│
└─ WARNING (5xx)
   ├─ VAL-501: Unused state definition
   ├─ VAL-502: Unreachable code (dead branch)
   ├─ VAL-503: Performance issue detected
   └─ VAL-504: Vague or ambiguous identifier

SEVERITY LEVELS:
  ERROR (1, 2, 3, 4xx): Blocks execution; must be fixed
  WARNING (5xx): Execution may proceed; recommended fix
  INFO: Suggestions only; no action required
```

## Error Recovery Strategies

### Strategy 1: Auto-Correction (Best Effort)

The auto-correction strategy maps error codes to fix suggestions. The helper functions referenced below (`suggest_closest_operator`, `suggest_closest_identifier`) are specified here as part of the correction interface; their implementations will use Levenshtein distance matching against the valid operator/identifier lists and are deferred to **v1.2 — Validator Module**.

```
AUTO-CORRECTION SPECIFICATION:

  Error "VAL-101" (Invalid operator keyword):
    → Find closest valid operator name using Levenshtein distance
    → Suggest replacement (e.g., "Acton:" → "Did you mean 'Action:'?")

  Error "VAL-102" (Unbalanced bracket/parenthesis):
    → Suggest insertion of closing delimiter at position

  Error "VAL-201" (Incomplete operator):
    → Suggest required clause (e.g., "Add 'THEN:' after 'IF:'")

  Error "VAL-301" (Undefined identifier):
    → Find closest defined identifier using Levenshtein distance
    → Suggest replacement (e.g., "State:Onlne" → "Did you mean 'State:Online'?")

  Default:
    → No auto-correction available; provide manual fix instructions
```

### Strategy 2: Error Aggregation (Don't Fail on First Error)

Rather than stopping at the first error, the validator should collect all errors in a single pass. This maps directly to the 5-stage pipeline defined above — each stage appends errors to a shared list. The `HaikuValidator` class (below) implements this pattern via its `_validate_syntactic()`, `_validate_semantic()`, `_validate_referential()`, `_validate_completeness()`, and `_validate_execution()` methods, aggregating results in `self.errors` and `self.warnings`.

```
ERROR AGGREGATION FLOW:

  1. Run syntactic checks  → append errors
  2. Run semantic checks   → append errors
  3. Run referential checks → append errors
  4. Run completeness checks → append errors
  5. Run execution checks   → append errors
  6. Sort all errors by position for logical reading order
  7. Return complete error list
```

### Strategy 3: Recovery Checkpoints (Interactive Repair)

For interactive use (e.g., CLI or Streamlit UI from v2.1), the validator can offer users a repair workflow. This is a **design specification** for the interactive experience; the actual `apply_fix()` and `launch_editor()` functions will be implemented in the UI layer during Phase 2.

```
INTERACTIVE REPAIR FLOW:

  For each validation error:
    1. Display error message and context
    2. Offer options:
       [1] Accept suggested fix (apply auto-correction from Strategy 1)
       [2] Skip this error and continue validation
       [3] Edit haiku string manually (open in editor)
       [4] Abort validation entirely
    3. Apply user's choice and proceed to next error

  Implementation notes:
    - "Apply fix" modifies the haiku string in-place and re-validates
    - "Edit manually" opens the haiku in the configured text editor
    - Both functions are UI-layer concerns (v2.1 — Streamlit Dashboard)
    - Phase 0 focuses on specifying the repair options, not implementing the UI
```

## Validation Pipeline Implementation (Research Prototype)

> **Scope:** This validator is a *research-phase prototype* demonstrating how the 6 validation rules map to a multi-stage pipeline. The `_validate_syntactic()` method depends on the `HaikuParser` tokenizer from v0.0.2c; in Phase 0, both files exist as specifications. Production implementation occurs in **v1.2 — Validator Module**, where the parser and validator are proper Python modules in the project source tree.

```python
#!/usr/bin/env python3
"""
Haiku Protocol Validation Pipeline v0.0.2d — Research Prototype

Demonstrates multi-stage validation with error aggregation.
Depends on HaikuParser from v0.0.2c (research sketch).
Production implementation is in v1.2 — Validator Module.
"""

from typing import List, Tuple
from dataclasses import dataclass
from enum import Enum

class ErrorSeverity(Enum):
    INFO = 0
    WARNING = 1
    ERROR = 2

@dataclass
class ValidationError:
    code: str              # VAL-001, VAL-002, etc.
    severity: ErrorSeverity
    message: str           # User-friendly message
    position: int          # Position in haiku string
    suggestion: str = ""   # Suggested fix (if available)
    details: str = ""      # Additional context

class HaikuValidator:
    def __init__(self, haiku: str, stop_on_error: bool = False):
        self.haiku = haiku
        self.stop_on_error = stop_on_error
        self.errors: List[ValidationError] = []
        self.warnings: List[ValidationError] = []

    def run(self) -> Tuple[bool, List[ValidationError]]:
        """
        Run full validation pipeline.
        Returns: (is_valid, error_list)
        """
        # Stage 1: Syntactic validation
        if not self._validate_syntactic():
            if self.stop_on_error:
                return (False, self.errors)

        # Stage 2: Semantic validation
        if not self._validate_semantic():
            if self.stop_on_error:
                return (False, self.errors)

        # Stage 3: Referential validation
        self._validate_referential()

        # Stage 4: Completeness validation
        self._validate_completeness()

        # Stage 5: Execution validation
        self._validate_execution()

        is_valid = len(self.errors) == 0
        return (is_valid, self.errors + self.warnings)

    def _validate_syntactic(self) -> bool:
        """RULE-001: Syntactic Well-Formedness"""
        try:
            # NOTE: In production (v1.2), this import resolves to
            # haiku_protocol.parser.HaikuParser. In Phase 0 research,
            # this references the parser sketch from v0.0.2c.
            from haiku_protocol.parser import HaikuParser  # v1.2 module path
            parser = HaikuParser()
            tokens = parser.tokenize(self.haiku)
            # Basic tokenization passed
            return True
        except SyntaxError as e:
            self.errors.append(ValidationError(
                code="VAL-001",
                severity=ErrorSeverity.ERROR,
                message=f"Syntax error: {e}",
                position=getattr(e, 'offset', 0),
                suggestion="Check operator spelling and bracket balance"
            ))
            return False

    def _validate_semantic(self) -> bool:
        """RULE-002: Operator Completeness"""
        # Check IF without THEN
        if "IF:" in self.haiku and "THEN:" not in self.haiku:
            pos = self.haiku.find("IF:")
            self.errors.append(ValidationError(
                code="VAL-002",
                severity=ErrorSeverity.ERROR,
                message="IF clause missing required THEN clause",
                position=pos,
                suggestion="Add 'THEN:' with statement after IF clause"
            ))
            return False

        # Check WARN without consequence
        import re
        warn_pattern = r'WARN:\w+\s*(?!->)'
        if re.search(warn_pattern, self.haiku):
            pos = self.haiku.find("WARN:")
            self.errors.append(ValidationError(
                code="VAL-002",
                severity=ErrorSeverity.ERROR,
                message="WARN clause missing required consequence",
                position=pos,
                suggestion="Add '-> Consequence_Identifier' after WARN identifier"
            ))
            return False

        return True

    def _validate_referential(self):
        """RULE-003: Reference Definition"""
        # Extract all referenced identifiers
        import re
        states = re.findall(r'State:(\w+)', self.haiku)
        actions = re.findall(r'Action:(\w+)', self.haiku)

        # Build set of defined states
        defined_states = set()
        for state in re.findall(r'State:(\w+)', self.haiku):
            defined_states.add(state)

        # Check for undefined references in REQUIRES
        for match in re.finditer(r'REQUIRES\s+State:(\w+)', self.haiku):
            state = match.group(1)
            if state not in defined_states:
                # May be external; add warning
                self.warnings.append(ValidationError(
                    code="VAL-003",
                    severity=ErrorSeverity.WARNING,
                    message=f"Undefined state: '{state}' (may be external)",
                    position=match.start(),
                    suggestion=f"Define 'State:{state}' or document in REF:"
                ))

    def _validate_completeness(self):
        """RULE-004: Circular Dependency Detection"""
        # Simplified check: detect basic circular patterns
        import re
        # This would need a full dependency graph analysis
        # Placeholder: detect self-referential REQUIRES
        if re.search(r'Action:(\w+).*REQUIRES.*State:\1', self.haiku):
            self.errors.append(ValidationError(
                code="VAL-004",
                severity=ErrorSeverity.ERROR,
                message="Circular dependency detected",
                position=0,
                suggestion="Review dependency chain for cycles"
            ))

    def _validate_execution(self):
        """RULE-005: Verifiable Verification Checks"""
        import re
        verify_checks = re.findall(r'VERIFY:(\w+)', self.haiku)

        vague_terms = ['OK', 'Working', 'Good', 'Done', 'Successful']
        for check in verify_checks:
            if any(vague in check for vague in vague_terms):
                pos = self.haiku.find(f"VERIFY:{check}")
                self.warnings.append(ValidationError(
                    code="VAL-005",
                    severity=ErrorSeverity.WARNING,
                    message=f"Verification check '{check}' may not be automatable",
                    position=pos,
                    suggestion=f"Use specific check: VERIFY:Service_Responding_OK"
                ))

# Usage example:
if __name__ == "__main__":
    haiku = """
    Action:Deploy REQUIRES State:Online -> EXEC:deploy.sh;
    VERIFY:Service_Running
    """

    validator = HaikuValidator(haiku)
    is_valid, errors = validator.run()

    if is_valid:
        print("✓ Validation passed")
    else:
        print(f"✗ Validation failed ({len(errors)} issues):")
        for error in errors:
            print(f"  [{error.code}] {error.message}")
            if error.suggestion:
                print(f"    → {error.suggestion}")
```

## Troubleshooting

**Issue:** Validation too strict; cannot execute haikus with external references.
**Solution:** Convert strict errors to warnings for references resolvable via REF:; allow execution to proceed.

**Issue:** Verification checks are platform-specific.
**Solution:** Provide verification mapping file (platform-specific checks); allow decoder to skip unknown verifications.

**Issue:** Error messages too technical for non-engineers.
**Solution:** Use plain language; suggest concrete fixes; provide examples.
