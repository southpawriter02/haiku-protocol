### Attempto Controlled English (ACE)

**Focus:** Unambiguous, machine-processable English subset

**Key Characteristics:**
- Strict grammatical rules (no ambiguity)
- Vocabulary constraints (whitelist of approved terms)
- Compositional semantics (meaning from structure)
- Automated parsing to logic (FOL or DRS)

**Example ACE sentence:**
```
Every customer that buys a product receives a discount.
```

**Why relevant to Haiku Protocol:**
- **Semantic clarity:** ACE's elimination of ambiguity mirrors our goal of preserving meaning through structure
- **Grammar-driven compression:** ACE shows that constrained syntax can reduce cognitive load without losing information
- **Parsing automation:** Techniques for ACE parsing inform how Haiku should parse its own CNL grammar

**Limitations:**
- Verbose for complex statements
- Requires extensive vocabulary pre-definition
- Not designed for conversational fluency

---

### Common Logic Controlled English (CLCE)

**Focus:** Bridging business rules and formal logic

**Key Characteristics:**
- Expressive power between ACE and SBVR
- Explicit semantic roles (agent, patient, instrument)
- Hierarchical concept organization
- Support for quantifiers and negation

**Example CLCE rule:**
```
if { a Customer C has made a Purchase P } then
   { C is eligible for Loyalty Discount }
```

**Why relevant to Haiku Protocol:**
- **Semantic roles:** CLCE's explicit agent/patient/instrument structure aligns with how compression should preserve relationships
- **Hierarchical concepts:** Mirrors information architecture's taxonomy approach
- **Business logic translation:** Shows how natural language can encode rules compactly

**Limitations:**
- More formal than natural English
- Learning curve for non-technical users
- Overkill for simple information extraction

---

### SBVR (Semantics of Business Vocabulary and Rules)

**Focus:** OMG standard for capturing business semantics in natural language

**Key Characteristics:**
- Vocabulary-driven (define terms once, reuse everywhere)
- Structured rules (decision tables, rule sets)
- Bi-directional traceability (spec ↔ implementation)
- Industry-standard (finance, healthcare, aviation)

**Example SBVR rule:**
```
Vocabulary: Claim, Policy, Valid, Payout
Rule: A Valid Claim must be associated with a Policy.
Rule: A Payout must not exceed Policy Coverage Limit.
```

**Why relevant to Haiku Protocol:**
- **Vocabulary precision:** SBVR's term definition approach directly informs Haiku's token hierarchy
- **Rule clarity:** Structured rules show how to maintain complex relationships compactly
- **Reusability:** SBVR's vocabulary reuse reduces redundancy—core to semantic compression

**Limitations:**
- Heavy upfront vocabulary management
- Standards compliance adds overhead
- Not designed for real-time compression during inference

### 1. Taxonomy Design

**IA Definition:** Hierarchical organization of content by shared attributes, reducing cognitive load by chunking information into recognizable categories.

**Compression Implication:**
- **Inheritance:** A parent term's properties need not be restated for children
  - Before: "Alice, a software engineer, works on backend systems. Bob, a software engineer, works on frontend systems."
  - After (with taxonomy): "[Engineer: Alice, scope: backend], [Engineer: Bob, scope: frontend]"
  - Saves: ~30% tokens by factoring out shared "software engineer" property

- **Sibling Grouping:** Related items grouped together reduce whitespace and markers
  - Enables: "Engineers (Alice: backend, Bob: frontend)" vs. separate sentences

---

### 2. Controlled Vocabularies

**IA Definition:** Pre-defined, finite sets of terms used consistently to describe similar concepts, eliminating synonymy and variation.

**Compression Implication:**
- **Standardization:** One token per concept
  - Without vocab control: "bug", "issue", "defect", "problem" = 4 tokens for same concept
  - With vocabulary: "defect" only = 1 token, saves 75%

- **Aliases via mapping:** Store "bug" → "defect" in header; use "defect" in content
  - Haiku Protocol approach: Define once in CNL grammar, reference compactly in payload

**SBVR Example:**
```
Vocabulary:
  Term: Customer
  Definition: A party that purchases goods or services
  Aliases: Client, Buyer, Consumer

// In compressed message: All variants map to <Customer>
```

---

### 3. Metadata Schemas

**IA Definition:** Structured labels describing content properties (author, date, category, status), enabling machines to process without parsing body text.

**Compression Implication:**
- **Extraction vs. Parsing:** Structured metadata eliminates the need for natural language description
  - Before: "The defect was reported on March 15, 2025 by Alice Chen, is high priority, affects the login system"
  - After (with schema): ```<Defect><Reporter>Alice Chen</Reporter><Date>2025-03-15</Date><Priority>High</Priority><System>Login</System></Defect>```
  - Saves: ~40% by moving from narrative to attribute-based structure

- **Semantic Clarity:** A schema field is unambiguous; natural language requires inference
  - Reduces cognitive load on LLM → better compression preservation

---

### 4. Faceted Classification

**IA Definition:** Multi-dimensional categorization (e.g., Product by Color, Size, Brand) allowing users to navigate via independent attributes rather than rigid hierarchies.

**Compression Implication:**
- **Dimensional Reduction:** Express items via coordinates in a faceted space
  - Instead of: "Red medium Nike running shoe", "Blue large Adidas hiking boot"
  - Use facets: Product[Color:Red, Size:M, Brand:Nike, Type:Running] | Product[Color:Blue, Size:L, Brand:Adidas, Type:Hiking]
  - Saves structure by factoring facet labels

- **Orthogonal Axes:** Avoids combinatorial explosion of hierarchies
  - Haiku Protocol can use faceted structure to compress nested information

**Example:**
```
# Before (narrative)
"The login issue affects Windows and Mac, for both Chrome and Firefox"

# After (faceted)
Issue[OS:{Windows, Mac}, Browser:{Chrome, Firefox}]
# Saves: implicit cross-product relationship, 50% token reduction
```

---

### 5. Information Scent

**IA Definition:** Clarity of navigational cues and labels that help users quickly understand if they're on the right path, reducing exploratory navigation.

**Compression Implication:**
- **Semantic Signposts:** Well-labeled sections allow readers to infer meaning without reading full content
  - Haiku Protocol's grammar acts as information scent: labels signal semantic role
  - Example: `<QUESTION>What is the capital?</QUESTION>` vs. ambiguous "the capital"

- **Reduced Ambiguity:** Clear labels = fewer tokens needed for clarification
  - Saves disambiguation questions, improves downstream LLM performance

- **CNL Research (1990–2010):** Focused on knowledge representation and automated reasoning
  - Result: Unambiguous parsing, but too formal for human fluency

- **IA Maturation (2000–2020):** Applied to web, software, content systems
  - Result: Best practices for organizing complex information, but no semantic compression

- **LLM Era (2022–present):** Prompts become the new medium
  - Problem: LLMs have limited context windows; compression is essential
  - Solution: Combine CNL's unambiguity with IA's organization to design compressible language

1. Formally unambiguous (no parsing errors)
2. Informationally dense (IA-optimized organization)
3. Compressible (structured format reduces redundancy)
4. Human-writable (tech-writer-friendly syntax)

## Key Theoretical Concepts

### Semantic Density

**Definition:** Information bits per token, or how much meaning is encoded in minimal syntax.

**Formula:**
```
Semantic Density = (Unique semantic propositions) / (Token count)
```

**Example:**
```
# Low semantic density (narrative)
"The customer Alice Chen, who works in engineering,
 submitted a bug report on March 15 about a login issue
 affecting Chrome on Windows."
Tokens: 25, Propositions: 5 → Density = 0.20

# High semantic density (structured)
Bug[Customer:Alice, Role:Engineer, Date:2025-03-15,
    Issue:Login, Browser:Chrome, OS:Windows]
Tokens: 12, Propositions: 5 → Density = 0.42 (2.1x denser)
```

**Haiku Protocol's Goal:** Achieve >0.5 semantic density through structured CNL grammar.

---

### Information Entropy & Redundancy

**Definition (Entropy):** Shannon entropy measures the average information content; high entropy = high information per symbol.

**Definition (Redundancy):** Repeated information or contextual clues that could be factored out.

**Compression Mechanism:**
```
Redundancy Identification:
  1. Repeated terms → Vocabulary reference
  2. Implied context → Factored to parent/header
  3. Synonyms → Standardized via controlled vocab
  4. Structural patterns → Templated via schema

Redundancy Elimination:
  Result: Higher entropy per token, lower total tokens
```

**Example:**
```
# High redundancy (implicit context)
"The user Mary accessed the system on Tuesday.
 The user John accessed the system on Wednesday.
 The user Sarah accessed the system on Thursday."

# Low redundancy (factored)
System.Access[User:{Mary, John, Sarah},
              Date:{Tue, Wed, Thu}]
```
